Tool use lets Claude request that your application run a specific function on its behalf. You define each tool with a name, a description, and a schema describing its expected inputs. When Claude determines a tool is needed to answer a request, it returns a tool-use block containing the tool name and the arguments it wants to use, rather than a plain text reply. Your code is responsible for actually executing the corresponding function and returning the result back to Claude in a follow-up message, at which point Claude can produce a final answer grounded in that real data. Multiple tool calls can be requested within a single turn, and your code should handle each one before continuing the conversation.

Prompt caching lets you reuse a previously processed portion of a prompt instead of reprocessing it on every request. This is especially valuable for long, mostly-static content such as system instructions, large reference documents, or extensive tool definitions that stay the same across many calls. Marking a cache breakpoint tells the system to store everything up to that point so a later request with an identical prefix can skip reprocessing it, cutting both latency and cost. Caches are not permanent; they expire after a period of inactivity, so caching works best for content that gets reused frequently within a short window rather than accessed only occasionally.

Embeddings convert a piece of text into a list of numbers that capture its meaning. Texts with similar meaning produce numerically similar embeddings, even when they share few or no exact words. This property is the foundation of semantic search: instead of matching keywords, you compare the mathematical distance between embeddings to find content that is conceptually related to a query. Anthropic does not currently offer a dedicated embeddings model directly through the Claude API, so many applications pair Claude with a separate embeddings provider for this step of a retrieval pipeline.

Streaming allows a model's response to be delivered incrementally, piece by piece, rather than waiting for the entire reply to finish generating before any of it is returned. This is particularly useful for chat interfaces, where showing partial output as it's generated creates a much more responsive feel for the person waiting on an answer. When streaming is combined with tool use, the individual pieces of a tool-use request may arrive incrementally as well, and the full request should be assembled before it is executed.

Structured outputs let you constrain a model's reply to a specific, predictable shape rather than free-form text, which is useful whenever the output needs to be consumed by code instead of a person. One common technique is to define a tool that represents the exact structure you want, and force the model to use that tool rather than letting it choose freely, so the arguments it returns can be read directly as structured data without needing to parse a plain text reply.

A model's context window is the maximum amount of text, measured in tokens, that it can take into account within a single request, including the conversation history, any documents provided, and the model's own reply. As conversations grow longer or more documents are added, older or less relevant content may need to be summarized, compressed, or dropped to stay within this limit while preserving the information most relevant to the current request. Managing what stays in versus what gets removed from the context window as an application scales is one of the central challenges in building reliable, long-running agents.

Retrieval augmented generation, commonly called RAG, is an approach for grounding a model's responses in external, private, or up-to-date information that wasn't part of its training data. Rather than sending an entire knowledge base to the model with every request, relevant pieces of content are first identified through a search step, typically using embeddings and a vector database, and only those relevant pieces are included in the prompt. This keeps requests smaller and more focused while still allowing the model to answer using specific, real information rather than relying solely on what it learned during training.

Extended thinking allows a model to reason through a problem more deliberately before producing its final response, which can improve performance on tasks that benefit from multi-step reasoning, such as complex analysis or nontrivial coding problems. The reasoning itself is exposed as a distinct part of the response, separate from the final answer, and applications can choose whether or how much of that reasoning process to surface to an end user.

Batch processing allows a large number of independent requests to be submitted together and processed asynchronously, rather than sent one at a time and waited on individually. This approach is well suited to workloads that don't need an immediate response, such as bulk content generation, large-scale evaluation runs, or processing a big backlog of documents, and can offer meaningfully lower cost compared to making the same number of requests synchronously.

Citations allow a model's response to reference specific parts of the source documents it was given, so that claims in the answer can be traced back to exactly where in the source material they came from. This is particularly useful in applications where trust and verifiability matter, such as research assistants or systems answering questions over legal or medical documents, since it lets a person quickly check whether the model's answer is actually supported by the underlying source.
